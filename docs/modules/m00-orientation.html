How This Practicum Works

A fleet of coding agents is not one clever model. It is several narrow agents, each with its own instructions, tools, and checks, passing work to each other through files a human can read. This module shows you the fleet you will build, how the lessons and labs fit together, the codebase your agents will work on, and the safety rules that apply from the first lab.

The fleet you will build

A coding agent is a language model running in a loop with tools that read and change a codebase: it reads files, edits them, runs commands, and decides what to do next from what it sees. Claude Code is one. GitHub Copilot's agent and Devin are others.

One agent can fix a bug. A fleet takes on the whole software development lifecycle (SDLC) by splitting it into stations, each run by a narrow agent. A station has four parts:

  • A trigger: what starts it (an issue is opened, a label is added, CI fails, a schedule).
  • An agent: instructions, a model, and only the tools that job needs.
  • A handoff: a file the next station reads, such as labels, a spec, a branch, or a review.
  • A gate: a check that must pass before work moves on, enforced by code or by a person.
flowchart LR
  T[Triage] -->|labels| P[Plan]
  P -->|spec.md| B[Build]
  B -->|branch| R[Review]
  B <-->|tests| X[Test]
  R -->|approved PR| L[Release]
  L --> O[Operate]
  O -.->|new issues| T
  H[Heal] -.->|fix red CI| B
  Q[Learn] -.->|harness changes| T

By the end of Level 1 you will have written every one of these agents, the hooks that keep them honest, a Python script that runs them in order, the GitHub Actions workflows that trigger them, a healer that fixes red builds within strict limits, and an evaluation set that tells you whether a change to your fleet made it better or worse.

Which of those stations would you trust an agent with today, with no human check at all? Keep your answer. You'll revisit it after M04, when you've seen what gates can enforce.

Remember: a fleet is stations, handoffs, and gates. Each agent is narrow, and the files between them are what make the whole thing reviewable.

The model and the harness

People say "the agent did something dumb" and blame the model. Usually the problem is somewhere else. A useful way to think about it:

agent = model + harness

The harness is everything except the model: the instructions it reads, the tools it can call, the permissions on those tools, the checks that run on its work, and the loop that drives it. Claude Code ships with a builder harness (its system prompt, its built-in tools, its loop). On top of that you build a user harness: the files in your repository and your CI that shape what the agent does in your codebase.

Builder harness (Claude Code provides)

  • The agent loop and context management
  • Built-in tools: Read, Edit, Write, Bash, Grep, Glob, Agent, ...
  • Permission modes and the permission system
  • Hook events, subagents, skills, headless mode

User harness (you write)

  • AGENTS.md and CLAUDE.md instructions
  • Subagent definitions in .claude/agents/
  • Skills in .claude/skills/
  • Hooks and settings in .claude/settings.json
  • Tests, lint rules, CI workflows, and evals

This course is about the user harness. When an agent you wrote slips, the question is always the same: which instruction, tool limit, or check would have stopped that? Then you add it. That habit has a name, harness engineering, and you will practise it in every module.

Remember: you can't change the model, but you own the harness. Treat each agent mistake as a missing guide (something that steers it before it acts) or a missing sensor (something that checks its work afterward).

fleetlab: practice in the browser

Lesson cells run real Python in your browser. They can import fleetlab, a small helper library written for this course. It never calls a model. It does the deterministic parts of agent work that you can learn and test anywhere:

  • fleetlab.check_agent(text) parses a subagent file and lists every problem, including fields Claude Code would silently ignore.
  • fleetlab.pre_tool_use(...) and fleetlab.stop(...) build the JSON payloads that Claude Code sends to hooks; fleetlab.run_hook(main, payload) runs your hook code against them.
  • fleetlab.parse_stream(text) reads the transcript of a headless run.

Try it. This cell checks a subagent definition that has one mistake. Run it with the button or Ctrl/⌘+Enter, then fix the mistake and run it again.

The field is spelled maxTurns. With maxturns, Claude Code would load the agent happily and give it no turn limit at all. Nothing would warn you. That is exactly the kind of failure the harness has to catch, because the model never will.

The same library runs on your machine in the labs, where the checks use it to read your files. Everything it can do is listed in the fleetlab reference.

Labs: build it on your machine

Lessons teach and exercises drill. Labs are where you build the real thing: agent files, hooks, settings, scripts, and workflows that Claude Code will actually load. Every lab follows the same cycle, run from the root of this repository:

pixi install                 # once
pixi run labs                # list labs and whether you've started them
pixi run start m00-lab1      # copy the starter into work/m00-lab1/
# read labs/m00-lab1/README.md, then do the work in work/m00-lab1/
pixi run grade m00-lab1      # run the lab's checks against your work
pixi run grade-live m02-lab1 # optional: also run checks that call the real claude CLI

Grading copies your workspace to build/labs/<lab>/ first, so checks can run your hooks and scripts without touching your files. Read the check output like a code review: each failure says what was expected and why.

This is deliberate. The point of the course is that you write the agents. Each lab's README is the specification and its checks are the acceptance test. The repository's CI runs pixi run check-labs, which proves every untouched starter fails its checks, so a green grade can't happen by accident. If you get stuck, the lesson's exercises and hints cover every skill a lab needs.

Most checks are deterministic: they parse your files, feed your hooks recorded payloads, and run your scripts against fixture transcripts. You don't need an API key for them. Live checks are the exception: with grade-live they run your agent with the real claude CLI and look at what it did. They skip themselves when the CLI isn't installed.

Meet shelf, the codebase your agents work on

Every lab gives your agents the same small project to work on: shelf, a command-line tool for tracking books. It lives in sample/ and each lab copies it into your workspace.

sample/
├── README.md
├── shelf/
│   ├── __main__.py      # python -m shelf
│   ├── cli.py           # add, list, search
│   ├── models.py        # the Book dataclass
│   └── store.py         # load, save, search, by_year
├── tests/               # pytest suite (all green today)
└── issues/              # five open issues, as Markdown

The tests pass, but the code is not correct. The issues describe real bugs the tests don't cover yet, a reasonable feature request, a request too vague for any agent, and one issue that tries to give your agents orders. You'll meet all of them again: the triager has to classify them, the builder has to fix them, and the reviewer has to catch a fix that hides a bug instead of removing it.

Open sample/issues/ and read all five. Which would you give to an agent? Which would you send back to the reporter? One of them contains instructions addressed to AI agents. What should an agent do when it reads them?

Working safely with agents

Coding agents run real commands with your permissions. Four rules apply from the first lab:

  1. Work in a sandbox. Run agents in this repository's work/ directory, a throwaway branch, a git worktree, or a container. Never point a new agent at a repository you can't afford to reset.
  2. Keep credentials out of reach. API keys live in your environment or your login, never in a file the agent can read and never in a commit. Agents in this course never need production credentials.
  3. Treat everything the agent reads as untrusted input. Issue text, web pages, log files, and dependency READMEs can contain instructions. That's called prompt injection. The defence is not a better prompt; it's a harness where the agent can't do the dangerous thing (issue #5 asks it to push to main, which your M04 hook will block).
  4. Least privilege by default. Give each agent the fewest tools and permissions its job needs. A reviewer that can't edit files can't "helpfully" rewrite your code.

Never run an agent with --dangerously-skip-permissions (bypass mode) outside a disposable container or VM with no credentials and no network access you care about. In that mode nothing asks before it acts.

Practice

Two warm-ups with fleetlab. They introduce the two shapes you'll handle most: agent files and hook payloads.

The variable agent holds a subagent definition with three problems: a field name typo, an unknown tool, and a name that doesn't match its file name planner.md. Fix the text so that fleetlab.check_agent(agent, "planner.md").problems is empty. Keep the agent read-only: it must not be able to edit files or run commands.

Hint

Run print(fleetlab.check_agent(agent, "planner.md").problems) and fix each message. Grep and Glob already cover searching; there is no Search tool.

Show solution
agent = """---
name: planner
description: Plans a change before code is written. Use after triage.
tools: Read, Grep, Glob
maxTurns: 25
---

You read the code and write a plan. You never edit files.
"""

When Claude Code is about to run a shell command, it can send a hook a JSON payload like the one fleetlab.pre_tool_use("Bash", {"command": "git push origin main"}) builds. Write describe(payload) that returns a one-line string "<tool>: <command>" for Bash payloads (for example "Bash: git push origin main") and just the tool name for any other tool.

Hint

The tool name is payload["tool_name"] and its arguments are in payload["tool_input"]. Print the payload to see every field.

Show solution
def describe(payload):
    tool = payload["tool_name"]
    if tool == "Bash":
        return f"{tool}: {payload['tool_input']['command']}"
    return tool

Quiz

Recap

  • A fleet is stations (trigger, agent, handoff, gate) covering the SDLC: triage, plan, build, test, review, release, operate, plus loops that heal and learn.
  • Agent = model + harness. Claude Code provides the builder harness; you write the user harness. Fix slips in the harness by adding a guide or a sensor.
  • fleetlab checks agent files, builds hook payloads, runs hook code, and reads transcripts, in the browser and in lab checks. It never calls a model.
  • Labs: pixi run start, write, pixi run grade. No solutions; checks are the spec. Live checks are optional.
  • shelf is the codebase every lab uses; its issues include real bugs, a vague request, and a prompt injection.
  • Safety: sandbox, credentials out of reach, untrusted input, least privilege.
