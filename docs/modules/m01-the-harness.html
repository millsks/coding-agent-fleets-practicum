The Harness

Before you write your own agents, look at the one you already have. Claude Code is a model running in a loop with tools, permissions, and settings around it. This module takes that harness apart: what the loop does, which tools it has, who decides whether a tool call runs, how to run it without a terminal, and how to read the transcript it leaves behind. Every agent in your fleet runs inside this same harness.

The loop inside Claude Code

Under the interface, Claude Code runs the same loop every agent runs. You send a task. The model replies either with text or with one or more tool calls. Claude Code runs each call (if it's allowed), sends the results back, and asks the model again. This repeats until the model replies without asking for a tool. Each request and response is one turn.

A useful way to think about what happens across those turns is three phases that repeat:

Gather

Read files, search with Grep and Glob, read the spec, look at logs and git diff. The agent builds the context it needs to act.

Act

Edit and write files, run commands, call MCP tools, hand a sub-task to a subagent.

Verify

Run the tests and linters, re-read the diff, compare the result with what was asked. Then go around again or stop.

flowchart LR
  Task --> G[Gather] --> A[Act] --> V[Verify]
  V -->|not done| G
  V -->|done, out of turns, or blocked| Stop

Most agent failures are this loop going wrong in a recognisable way. The agent stops too early, claiming success without running the tests. It loops, making the same failing edit again and again. It drifts, editing files nobody asked about. It starves, acting before it has read the code it's changing. You'll learn to spot each of these in transcripts at the end of this module, and to block them with hooks in M04.

Remember: the model decides what to do next; the harness decides whether it's allowed, runs it, and decides when the loop must end.

Built-in tools

A tool is a function the model can ask the harness to run. Claude Code ships with a set of built-in tools. These are the ones every agent definition in this course refers to by name:

ToolWhat it doesChanges state?
ReadRead a file (or part of one)No
GrepSearch file contents with a regular expressionNo
GlobFind files by name patternNo
EditReplace an exact string in a fileYes
WriteCreate or overwrite a fileYes
BashRun a shell commandYes: anything a shell can do
AgentStart a subagent with its own context and toolsWhatever the subagent can do
WebFetch, WebSearchRead a URL, search the webNo, but they bring in untrusted text
TodoWriteKeep a task list during a sessionOnly the session's list

Two things in that table matter more than they look. First, Bash is effectively every tool: an agent with Bash can edit files with sed, delete them, or push to a remote. An agent you mean to be read-only must not have it, or must have it limited by permission rules. Second, tools from MCP servers appear alongside these with names like mcp__github__get_issue (server github, tool get_issue). They follow the same permission system.

A "reviewer" agent has Read, Grep, Glob, and Bash so it can run git diff. Can it change your code? What would you add to make sure it can't?

Who decides: permission modes and rules

Every tool call passes through the permission system before it runs. Two things decide the outcome: the session's permission mode and your permission rules.

Permission modes

ModeBehaviourUse it for
default (also called manual)Asks before anything that isn't pre-approved; reads in your working directory don't need approvalInteractive work
acceptEditsFile edits and common filesystem commands run without asking; other shell commands still need a ruleBuilders you're watching
planRead-only: the agent explores and proposes, but doesn't change anythingPlanning, risky changes
autoA classifier reviews each action instead of asking youLong unattended runs with oversight
dontAskAnything that would prompt is denied; only pre-approved actions runLocked-down CI
bypassPermissionsNothing asks. Everything runsOnly disposable sandboxes

Permission rules

Rules live in a settings file under permissions, in three lists: allow (run without asking), ask (always ask), and deny (never run). A rule names a tool, optionally with a pattern in parentheses:

{
  "permissions": {
    "allow": ["Read", "Bash(python -m pytest *)", "Bash(git diff *)"],
    "deny":  ["Bash(git push *)", "Read(.env)", "Edit(.github/workflows/**)"]
  }
}

For Bash, a trailing  * (a space, then a star) means "any command that starts with this". The space matters: Bash(git diff *) matches git diff main but not git diff-index, while Bash(git diff*) matches both. Deny rules win over allow rules, and the same rule syntax is used for the --allowedTools flag in headless runs.

Settings files and which one wins

Permission rules, hooks, environment variables, and many other options live in JSON settings files. Claude Code reads several and merges them:

FileScopeCommit it?
~/.claude/settings.jsonYou, in every projectNo (it's in your home directory)
.claude/settings.jsonEveryone working in this projectYes: this is where a fleet's shared rules and hooks go
.claude/settings.local.jsonYou, in this projectNo: gitignore it
--settings <file-or-json>One runIt's a flag, so whatever script passes it
Managed settingsAn organization's administratorsDeployed by IT, not by you

When files disagree on a single value, the more specific one wins: managed settings over everything, then command-line settings, then local, then project, then user. Lists such as hooks are combined across files rather than replaced. For a fleet, the rule of thumb is simple: anything every agent must obey goes in the committed .claude/settings.json, so it travels with the repository into every worktree and CI job.

At work you may see settings you didn't write and can't override. That's managed settings doing its job. Design your harness so that its real enforcement (tests, hooks, CI) still works when an administrator has locked other options down.

Running without a terminal: headless mode

A fleet runs agents from scripts and CI, not from a chat window. claude -p "<prompt>" (or --print) runs one task non-interactively and exits: 0 on success, non-zero when the run fails. These are the options you'll combine with it most:

OptionWhat it does
--output-format text|json|stream-jsonjson prints one object with the result, session id, cost, and usage; stream-json prints one JSON event per line as the run happens (add --verbose)
--allowedTools "Read,Grep,Bash(git diff *)"Pre-approve tools using permission-rule syntax
--permission-mode dontAsk|acceptEdits|plan|...Set the baseline mode for the run
--max-turns NStop after N agentic turns
--append-system-prompt "..."Add instructions while keeping Claude Code's defaults
--json-schema '{...}'With json output, return schema-valid data in structured_output
--bareSkip auto-discovery: no hooks, skills, subagents, plugins, MCP servers, or CLAUDE.md unless you pass them with flags
--resume <session-id>, --continueContinue an earlier conversation

In a headless run nobody can answer a permission prompt, so a call that would need approval is denied unless a rule, a mode, or a hook allows it. That's a feature: a CI job should only be able to do what you listed.

--bare deserves a closer look. Without it, claude -p loads everything an interactive session would, including the hooks in the repository's .claude/settings.json and the servers in its .mcp.json, without the trust prompt an interactive session shows. In CI that means a pull request could change what runs. With --bare, only what you pass on the command line applies, so every run is the same everywhere. It also skips your subscription login and reads ANTHROPIC_API_KEY from the environment.

# a read-only review that returns JSON, with a hard turn limit
claude --bare -p "Review the diff in change.patch for bugs. Report file:line for each." \
  --allowedTools "Read,Grep,Glob" \
  --max-turns 10 \
  --output-format json | jq -r '.result'

Remember: in scripts and CI use -p, list tools explicitly, cap turns, and prefer --bare with everything passed as flags. You'll build exactly this in Stage 2.

Reading a run

With --output-format stream-json --verbose, every event in the run is printed as one JSON object per line. Reading these transcripts is how you debug agents: you see exactly what the model was given, what it asked for, and what came back. The events that matter most:

  • {"type": "system", "subtype": "init", ...}: the session id, the model, and the tools available.
  • {"type": "assistant", "message": {"content": [...]}}: the model's text and its tool_use blocks, each with an id, a name, and an input.
  • {"type": "user", "message": {"content": [...]}}: the tool_result blocks sent back, each pointing at a call by tool_use_id, with is_error set when the tool failed.
  • {"type": "result", ...}: the last line, with subtype ("success" or an error kind), is_error, num_turns, total_cost_usd, and the final result text.

Failure signatures in transcripts

Each loop failure leaves a recognisable trace. Learn to look for these:

FailureWhat it looks like in the transcriptHarness fix (later modules)
Premature doneEdits, then a final message, with no test command after the last editA Stop hook that runs the tests (M04)
Doom loopThe same tool with the same input several times in a row, each result an errorTurn limits, error-signature checks, escalation (M04, Stage 2)
DriftEdits to files the task never mentionedA spec with "files in scope", a reviewer that checks it (M02)
Context starvationEdits before any Read or Grep of the file being changedBetter instructions and a map in AGENTS.md (M03)
Shallow fixA test file edited to remove or loosen an assertionA hook that keeps the builder out of tests/ (M04)

Practice

Five exercises on transcripts, permission rules, and headless commands. Tests build their own transcripts with make_run, a helper defined in the test code that turns a list of (tool, input, error?) steps into stream-json text.

Write tool_counts(stream_text) that returns a dictionary mapping each tool name to how many times it was called in the run, using fleetlab.parse_stream. Count subagent calls too.

Hint

fleetlab.parse_stream(text).calls is the list of calls; each has .name. The run object also has a method that does the counting.

Show solution
import fleetlab

def tool_counts(stream_text):
    return fleetlab.parse_stream(stream_text).calls_by_tool()

Write verified_after_last_edit(stream_text) that returns True when a Bash call whose command contains pytest comes after the last Edit or Write call. A run with no edits counts as verified. This is a detector for the premature-done failure.

Hint

Find the index of the last call whose name is Edit or Write. Then look at the calls after that index.

Show solution
import fleetlab

def verified_after_last_edit(stream_text):
    calls = fleetlab.parse_stream(stream_text).calls
    last_edit = -1
    for i, call in enumerate(calls):
        if call.name in ("Edit", "Write"):
            last_edit = i
    if last_edit == -1:
        return True
    return any(
        c.name == "Bash" and "pytest" in c.input.get("command", "")
        for c in calls[last_edit + 1:]
    )

Write doom_loop(stream_text, repeats=3) that returns True when the run contains repeats or more consecutive calls with the same tool name and the same input, all of which returned an error.

Hint

Walk the calls keeping a streak counter. A call continues the streak when it is an error and has the same (name, input) as the previous call in the streak. Otherwise reset: to 1 if the call is an error, to 0 if not.

Show solution
import json
import fleetlab

def doom_loop(stream_text, repeats=3):
    streak, previous = 0, None
    for call in fleetlab.parse_stream(stream_text).calls:
        key = (call.name, json.dumps(call.input, sort_keys=True))
        if call.is_error and key == previous:
            streak += 1
        elif call.is_error:
            streak = 1
        else:
            streak = 0
        previous = key if call.is_error else None
        if streak >= repeats:
            return True
    return False

Write decide(command, allow, deny) using the simplified Bash rule model from this module: a rule is Bash(<text>); if <text> ends with a space and a star it matches the prefix exactly or the prefix followed by a space; otherwise it must match the whole command. Deny wins over allow. Return "deny", "allow", or "ask".

Hint

Write a helper matches(rule, command) first. Strip Bash( and the closing parenthesis, then handle the two cases.

Show solution
def matches(rule, command):
    inner = rule[len("Bash("):-1]
    if inner.endswith(" *"):
        prefix = inner[:-2]
        return command == prefix or command.startswith(prefix + " ")
    return command == inner

def decide(command, allow, deny):
    if any(matches(r, command) for r in deny):
        return "deny"
    if any(matches(r, command) for r in allow):
        return "allow"
    return "ask"

Write review_command(prompt, max_turns=10) that returns the argument list (as for subprocess.run) for a read-only, reproducible headless review. It must start with "claude", use --bare and -p with the prompt, allow exactly the tools Read,Grep,Glob, set the turn limit, and ask for json output.

Hint

Every element of the list must be a string, including the number of turns. Tools go in one argument separated by commas.

Show solution
def review_command(prompt, max_turns=10):
    return [
        "claude", "--bare", "-p", prompt,
        "--allowedTools", "Read,Grep,Glob",
        "--max-turns", str(max_turns),
        "--output-format", "json",
    ]

Quiz

Recap

  • Claude Code runs the agent loop: gather, act, verify, repeat. The model chooses; the harness permits, runs, and stops.
  • Read-only tools: Read, Grep, Glob. State-changing: Edit, Write, and Bash, which can do anything.
  • Permission modes set the baseline; allow, ask, and deny rules refine it; deny wins; Bash(x *) is a prefix match and the space matters.
  • Shared rules and hooks belong in the committed .claude/settings.json. Managed settings beat everything.
  • Headless: claude -p, explicit --allowedTools, --max-turns, --output-format json or stream-json, and --bare for reproducible, safe CI runs.
  • Transcripts show what summaries hide: premature done, doom loops, drift, starvation, shallow fixes.
