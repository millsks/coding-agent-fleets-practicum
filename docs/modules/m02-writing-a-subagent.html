Writing a Subagent

Every station in your fleet is a subagent: a Markdown file that gives Claude a role, a prompt, a set of tools, and limits. This module covers every part of that file and, more importantly, how to write each part well: a description that makes delegation happen at the right moment, a prompt with a clear output and a clear point to stop, and tools that let the agent do its job and nothing else. You'll finish by writing the reviewer and test-writer your fleet will use from here on.

⏱ ~2.5 hoursPrerequisites: M01 The Harness
  • Explain what a subagent gives you (its own context, tools, and prompt) and what it costs
  • Write a subagent file in the right place, and predict which definition wins when names collide
  • Use the frontmatter fields deliberately: tools, disallowedTools, model, maxTurns, isolation, and others
  • Write descriptions that trigger delegation for the right tasks and not the wrong ones
  • Write prompts with a role, a scope, a process, an output format, and stop conditions
  • Choose least-privilege tools for a role, and test an agent against a seeded change

What a subagent is for

A subagent is a separate agent that the main conversation (or a script) can hand a task to. It runs with:

  • Its own context window. It starts fresh with its own prompt and only what it's given. The hundreds of lines it reads while working never land in the caller's context. Only its final answer comes back.
  • Its own prompt. The body of the file becomes its system instructions: a role and rules that don't have to compete with everything else the main session knows.
  • Its own tools and limits. A reviewer can be read-only even when the main session can edit files.

Those three properties are why a fleet is built from subagents. Isolation keeps each station's context small and focused. A separate prompt makes behaviour consistent. Separate tools enforce least privilege. And a fresh context is what makes a reviewer useful: an agent that didn't write the code doesn't share the author's blind spots.

The cost is that a subagent only returns a summary. If the caller needs every detail of what the subagent saw, it either has to ask for that detail in the output format or do the work itself. Subagents also start cold: each one re-reads what it needs, which costs tokens and time.

Claude Code includes some built-in subagents, notably Explore (fast, read-only searching), Plan (research before planning), and general-purpose. Yours sit alongside them.

Remember: use a subagent when a task is focused, its result can be summarised, and it benefits from a fresh context or tighter tools. Keep work in one session when the caller needs every detail.

Anatomy of a subagent file

A subagent is a Markdown file with YAML frontmatter. Only name and description are required. Everything after the closing --- is the subagent's system prompt.

---
name: reviewer
description: Reviews the current branch for bugs, security issues and scope creep. Use after code changes, before opening a pull request.
tools: Read, Grep, Glob, Bash
disallowedTools: Edit, Write
model: sonnet
maxTurns: 25
---

You review code. You never edit files.
...

Where it lives, and which definition wins

LocationScope
Managed settings directorySet by an organization; wins over project and user definitions with the same name
--agents '{...}' on the command lineOne session; highest priority among the ones you control, and not saved to disk
.claude/agents/This project; commit it so the whole team and CI get the same agents
~/.claude/agents/You, in every project
A plugin's agents/Wherever the plugin is enabled

Claude Code scans the agent folders recursively, so you can organise definitions in subfolders like agents/review/. When two definitions share a name, the higher-priority location wins. That's how you'd override a personal reviewer with the team's project reviewer, and how an administrator can pin one for everyone.

Claude Code ignores frontmatter fields it doesn't recognise, without warning. A misspelled field simply isn't applied. That's why every lab check (and the validator you'll put in your own CI) parses agent files with fleetlab.check_agent.

Subagents can start their own subagents (by default up to three levels below the main conversation). To stop a specific agent from delegating, leave Agent out of its tools. That's the right default for most stations: a reviewer that spawns more reviewers is hard to reason about.

Descriptions that trigger delegation

When you ask the main session to do something, Claude decides whether to hand it to a subagent by reading the descriptions of all available subagents. The description is a routing rule written in plain language. A good one says what the agent does and when to use it, with the trigger words a request would actually contain.

Weak

  • Helps with code. (matches everything, so it's useless)
  • Reviewer agent. (no trigger)
  • A 600-word essay about review philosophy (costs context in every session)

Strong

  • Reviews the current branch for bugs, security issues and scope creep. Use after code changes, before opening a pull request.
  • Writes failing tests that reproduce a reported bug. Use before fixing any bug.

Phrases like "Use proactively after code changes" make delegation more likely without being asked. You can always delegate explicitly too ("Use the reviewer subagent on this branch"), and scripts do exactly that. Descriptions are loaded into every session's context, so keep them to a sentence or two: Claude Code warns at startup when the combined descriptions of your custom subagents pass 15,000 tokens.

Two of your agents have the descriptions "Fixes bugs" and "Fixes failing CI builds". A user says "CI is red because of a bug in search". Which one should run? Rewrite the descriptions so the answer is obvious.

Prompts with a shape

The body of the file is the subagent's system prompt. Agents given a vague role ("You are a great reviewer") produce vague work. Agents given a shape produce work you can check. A reliable shape has five parts:

  1. Role and boundary. One sentence: what it does and what it never does. "You review code. You never edit files."
  2. Inputs. What it should read first: the spec, the diff, the failing log.
  3. Process. A few numbered steps. Not a script, but the order that avoids common mistakes (read before you act, run the tests before you finish).
  4. Output format. Exactly what to return, ideally in a form a script can check: labelled findings, a table, a JSON object, a final VERDICT: line.
  5. Stop conditions. When to stop and hand back instead of pushing on: the spec is wrong, a decision belongs to a human, the same fix failed twice.
You review code. You never edit files.

Inputs: the diff of the current branch against main (`git diff main...HEAD`) and the
spec in specs/ if there is one.

Process:
1. Read the whole diff, then the spec.
2. Check that every acceptance criterion is implemented and tested.
3. Look for bugs, missing error handling, security problems, and changes outside the spec's scope.

Output: one line per finding, `BLOCKING` or `NIT`, then file:line, the problem, and a fix.
End with exactly one line: `VERDICT: approve` or `VERDICT: changes requested`.

Stop and say so if there is no diff, or if the change needs a decision only a human can make.
Say plainly when you find nothing blocking. Do not invent problems to look thorough.

The last line matters more than it looks. Models asked to review tend to find something; telling it that "nothing blocking" is an acceptable answer cuts false alarms. The VERDICT: line matters because in Stage 2 a script will read it to decide whether the fleet moves on.

Remember: role and boundary, inputs, process, output format, stop conditions. If a script will read the output, make the format exact.

Least-privilege tools

Pick tools from what the role must do, not what might be handy:

RoleNeeds toTools
TriagerRead the issue and find the code areaRead, Grep, Glob (plus Bash for gh issue view, limited by rules)
PlannerRead code, write a specRead, Grep, Glob, Write
ImplementerRead, edit, run tests, delegate tests and reviewRead, Grep, Glob, Edit, Write, Bash, Agent, in a worktree
Test writerRead the spec, write tests, run themRead, Grep, Glob, Write, Edit, Bash, kept to tests/ by a hook
ReviewerRead the diff and the codeRead, Grep, Glob, Bash with disallowedTools: Edit, Write

Notice that tool lists alone can't express "only in tests/" or "only git diff". For that you combine tools with permission rules and hooks. The tools field is the coarse lock; hooks are the fine one.

Its prompt says it never edits, but nothing stops it. Remove Edit and add disallowedTools: Edit, Write, then run it again. can_write() stays true because of Bash: that's honest, since a shell can edit files. You'll close that gap with a hook in M04.

Model, effort, turns, and isolation

Model. Match the model to the stakes and the volume. Triage of every new issue is high-volume and simple: a small model is right. A plan or a review decides what code gets written or merged: use the strongest model you have. inherit uses the caller's model, which is convenient but makes cost depend on who called.

Turns. maxTurns stops a subagent after that many turns and returns what it has. Set it from what the job needs plus headroom: a reviewer that needs 40 turns is probably reading the whole repository. When a well-scoped agent keeps hitting its limit, that's a signal the task or the context is wrong, not that the limit is too low.

Isolation. isolation: worktree runs the subagent in a temporary git worktree, a separate checkout of the repository. Two builders working at once can't overwrite each other's files, and a failed attempt is just a worktree to throw away.

Background. Subagents run in the foreground by default, blocking the caller until they finish. Background subagents run while the caller keeps working, and their results arrive as notifications. By default up to 20 can run at once.

Using and testing a subagent

Once the file exists, there are three ways it runs:

  • Automatic delegation: the main session picks it from its description.
  • Explicit: "Use the reviewer subagent to review this branch."
  • As the main agent of a run: claude --agent reviewer, or from a script with -p. With --bare, pass definitions as JSON with --agents.

Test an agent the way you'd test code: with a fixed input and a known right answer. For a reviewer that means a seeded change: a diff you wrote with a bug you know about. For shelf, a good one "fixes" issue #1 by lower-casing the search term but not the titles, so the bug just moves. Run the reviewer on it several times. Does it find the bug every time? Does it report problems that aren't there? Does it end with the VERDICT: line? Change one thing in the prompt at a time and run again.

cd work/m02-lab1
git init -q && git add -A && git commit -qm base
git apply ../../labs/m02-lab1/seeded/bad-fix.patch   # the seeded change
claude -p "Use the reviewer subagent to review the uncommitted changes." --allowedTools "Read,Grep,Glob,Bash(git diff *)"

Model output varies from run to run. One good review proves little. Run the same seeded change three to five times before you trust a prompt change. Stage 2 turns this into an evaluation set you can rerun on every change to your fleet.

Write tools_for(needs). needs is a set drawn from "read", "search", "edit", "create", "run", and "delegate". Return the sorted list of the smallest set of Claude Code tools that covers them: read → Read; search → Grep and Glob; edit → Edit; create → Write; run → Bash; delegate → Agent.

Hint

A dictionary from need to a tuple of tools, then a set union, then sorted.

Show solution
NEED_TOOLS = {
    "read": ("Read",), "search": ("Grep", "Glob"), "edit": ("Edit",),
    "create": ("Write",), "run": ("Bash",), "delegate": ("Agent",),
}

def tools_for(needs):
    tools = set()
    for need in needs:
        tools.update(NEED_TOOLS[need])
    return sorted(tools)

Write description_problems(text) returning a list of strings, one per problem:

  • "too long" when longer than 250 characters;
  • "no trigger" when it contains neither "Use " nor "use ";
  • "too vague" when, lower-cased, it contains any of "helps with", "does stuff", "general purpose".

Report problems in that order. A good description returns an empty list.

Hint

Build the list with three independent if checks in the stated order.

Show solution
VAGUE = ("helps with", "does stuff", "general purpose")

def description_problems(text):
    problems = []
    if len(text) > 250:
        problems.append("too long")
    if "Use " not in text and "use " not in text:
        problems.append("no trigger")
    if any(v in text.lower() for v in VAGUE):
        problems.append("too vague")
    return problems

Write missing_parts(prompt) that returns, in this order, which of these parts a prompt is missing, using simple case-insensitive keyword checks:

  • "boundary": none of "never", "do not", "don't";
  • "output": none of "output", "report", "return";
  • "stop": none of "stop", "hand back", "escalate".
Hint

Lower-case the prompt once. A part is missing when not any(word in text for word in words).

Show solution
PARTS = [
    ("boundary", ("never", "do not", "don't")),
    ("output", ("output", "report", "return")),
    ("stop", ("stop", "hand back", "escalate")),
]

def missing_parts(prompt):
    text = prompt.lower()
    return [name for name, words in PARTS if not any(w in text for w in words)]

Write resolve(definitions). Each definition is a dict with "name" and "scope", where scope is one of "managed", "cli", "project", "user", "plugin" (highest priority first). Return a dict mapping each name to the scope of the definition that wins.

Hint

Give each scope a rank with ORDER.index(scope); for each name keep the definition with the lowest rank.

Show solution
ORDER = ["managed", "cli", "project", "user", "plugin"]

def resolve(definitions):
    winners = {}
    for d in definitions:
        current = winners.get(d["name"])
        if current is None or ORDER.index(d["scope"]) < ORDER.index(current):
            winners[d["name"]] = d["scope"]
    return winners

Quiz

Recap

  • A subagent has its own context, prompt, and tools, and returns a summary. Use one for focused work that benefits from a fresh context or tighter tools.
  • Files live in .claude/agents/ (commit them). Managed and --agents definitions win over project, which wins over user.
  • Always set tools and maxTurns; add disallowedTools as a second lock; use isolation: worktree for agents that edit.
  • The description is a routing rule: what it does and when to use it, in a sentence or two.
  • Prompts need a role and boundary, inputs, process, exact output, and stop conditions.
  • Test agents on seeded changes, several runs each, one prompt change at a time.
