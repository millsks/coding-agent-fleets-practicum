Context Engineering

An agent can only act on what is in its context window. Some of that you choose: the project instructions every agent reads, the skills it can pull in, the spec it's handed. The rest it gathers while working. This module is about choosing well: what loads at startup and what it costs, how to write the AGENTS.md every tool in your fleet will read, how skills load detail only when it's needed, and how to keep long runs from losing the plot.

  • Explain how CLAUDE.md files and imports load, and use AGENTS.md as one source of instructions for every tool

What's in the window before the agent starts

The context window is everything the model sees on a request: instructions, tool definitions, conversation so far, and tool results. It has a fixed size, every token in it costs money on every request, and models follow instructions less reliably as it fills with things that don't matter. Before your agent reads a single file of code, its window already holds:

WhatWho controls itTypical size
Claude Code's system prompt and built-in tool definitionsThe builder harnessLarge, fixed
CLAUDE.md files (and anything they import)YouWhatever you write
Names and descriptions of every skillYouA line or two each
Names and descriptions of every subagentYouA line or two each
Tool definitions from every connected MCP serverYou (by connecting servers)Can be very large
The task itself: the prompt, a spec, an issueWhoever starts the agentVaries

A common rough estimate is about four characters per token for English and code. Paste your own CLAUDE.md into the meter to see what it costs on every single request:

An agent makes 40 requests to fix a bug. A 6,000-token CLAUDE.md is sent with every one. How many tokens does it cost across the run? What if 4,000 of those tokens are a deployment runbook this agent never needs?

Remember: what loads at startup is paid for on every request and competes with the task for the model's attention. Load a short map up front; pull detail in when it's needed.

CLAUDE.md, imports, and AGENTS.md

CLAUDE.md is the file Claude Code reads for project instructions. It loads from several places and combines them:

  • ~/.claude/CLAUDE.md: your personal instructions for every project.
  • CLAUDE.md at the project root (and in parent directories above where you start): shared, committed instructions.
  • CLAUDE.md in a subdirectory: loaded when the agent works with files in that directory, so a package can carry its own notes.

A line of the form @path/to/file imports that file's contents. That's the key to working with more than one tool.

AGENTS.md is an open, cross-tool standard for the same job: a README for coding agents. A long list of tools read it, including GitHub Copilot, OpenAI Codex, Cursor, Gemini CLI, and Devin. If your fleet will ever run under more than one tool (Claude Code at home, Copilot or Devin at work), keep the shared instructions in AGENTS.md and make CLAUDE.md a thin pointer:

@AGENTS.md

## Claude Code notes

- The Stop hook runs `make test-fast` before you finish.

Now there is one source of truth. Claude Code reads AGENTS.md through the import; the other tools read it directly. Claude-only notes stay in CLAUDE.md.

Some tools read only the start of AGENTS.md (Devin, for example, includes the first 16 KiB). Put the most important things first and keep the whole file well under that.

Writing an AGENTS.md that earns its tokens

Every agent reads this file on every run, so every line must change what agents do. Three sections cover most of it:

  1. Commands. The exact commands to set up, test, lint, and run the project. Agents use these verbatim, so each one must work when pasted into a fresh checkout. A wrong command here is worse than none: every agent will run it, fail, and spend turns working out why.
  2. Map. Where things live, in a few lines. Which directory holds what, where tests go, what's generated. This replaces the knowledge a senior engineer carries in their head.
  3. Rules. The handful of non-negotiables: never weaken tests, change only files in the spec's scope, never commit secrets. Short, specific, and checkable.

Here's a compact example for a different project, a small invoicing service:

# AGENTS.md

Invoicing API (FastAPI + PostgreSQL). Read this first; procedures live in .claude/skills/.

## Commands
- Setup: `pixi install`
- Fast checks (run before finishing): `pixi run test-fast`
- Full tests: `pixi run test`
- Lint: `pixi run lint`

## Map
- `api/routes/`: one module per resource; handlers stay thin
- `api/billing/`: money logic; amounts are integer cents, never floats
- `migrations/`: generated by `pixi run makemigration`; never edit by hand
- `tests/`: mirrors `api/`

## Rules
- Change only the files listed in the spec's "Files in scope".
- Never delete, skip, or loosen a test to make it pass.
- Never commit secrets or `.env` files.

What it leaves out matters as much: no history of the project, no style rules a linter already enforces, no step-by-step procedures (those are skills), and no rule that must be guaranteed (those are hooks). A useful test for every line: would an agent behave differently without it? If not, delete it.

Remember: commands that run, a map, a few rules. Verify every command in a clean checkout. Delete lines that don't change behaviour.

Skills and progressive disclosure

A skill is a folder with a SKILL.md file that teaches an agent one procedure: how to cut a release, add a CLI command, write a migration. Skills follow the open Agent Skills format, which Claude Code, Copilot, Codex, Devin, and many other tools understand. In Claude Code, project skills live in .claude/skills/<name>/SKILL.md.

---
name: release-notes
description: Draft release notes from merged pull requests since the last tag. Use when preparing a release.
---

# Release notes

1. Find the last tag with `git describe --tags --abbrev=0`.
2. List merged pull requests since then.
3. Group them using the categories in [categories.md](categories.md).
...

What makes skills efficient is progressive disclosure, loading in three levels:

  1. Metadata (name and description): always in context, so the agent knows the skill exists and when to use it. A line or two.
  2. Body of SKILL.md: loaded only when the skill is used. Keep it under about 500 lines.
  3. Linked files (references, templates, scripts) in the skill's folder: read only if the body sends the agent there. Scripts can be run without being read at all.

So a fleet can carry dozens of procedures while paying, at startup, only for a line per skill. The skill's name must match its folder (lowercase, digits, and single hyphens), and its description, like a subagent's, is a routing rule: what it does and when to use it.

AGENTS.md, skill, or hook?

Every new rule you want agents to follow has a right home. Choosing wrongly either wastes context on every request or leaves something important to chance.

If the rule is…Put it inBecause
A fact every agent needs on every task (commands, layout, conventions)AGENTS.mdAlways loaded, shared across tools
A multi-step procedure needed only sometimesA skillLoaded only when used
Something that must never happen, or must always happenA hook (M04), plus CIEnforced by code; prose can be ignored
Specific to one roleThat subagent's promptOnly that agent pays for it
Specific to one taskThe spec or the promptExpires with the task

The most common mistake is putting a must in prose. "Always run the tests before finishing" in AGENTS.md is a request. A Stop hook that runs the tests is a guarantee. Keep the prose line if it helps the agent plan, but don't rely on it.

Keeping each agent's context focused

The context an agent gathers matters as much as what it starts with. Three habits keep it focused:

  • Delegate exploration. Searching a large codebase fills the window with files that turn out to be irrelevant. Hand that to a subagent (the built-in Explore agent is made for it) and get back a short summary of where things are.
  • Hand off files, not conversations. The builder shouldn't read the whole issue thread and the planner's reasoning. It should read specs/12.md: the decision, the files in scope, the acceptance criteria. Files are shorter, reviewable, and survive restarts.
  • Size tasks to the window. An agent asked to "refactor the billing module" will read far more than one asked to "extract the tax calculation from invoice.py into tax.py". Smaller tasks need less context and fail more cheaply.

When a long run approaches the limit, Claude Code compacts the conversation: it summarises earlier turns to make room. Summaries lose detail, so an instruction given once early in a long chat can fade. Constraints that must survive belong in files the agent re-reads (AGENTS.md, the spec), not in a message near the start. A subagent can lower its compaction threshold with autoCompactWindow, and one that doesn't need project instructions can skip them with omitClaudeMd: true.

Practice

Five exercises: budgeting the window, reading AGENTS.md like an agent does, writing a skill, deciding where rules belong, and finding what a truncating tool would miss.

Write startup_report(parts, calls). parts maps a name (like "CLAUDE.md") to its text. Return a dict with "tokens" (total estimated tokens using fleetlab.estimate_tokens), "per_run" (tokens times calls), and "largest" (the name with the most tokens).

Hint

Build a dict of tokens per part first, then max(tokens, key=tokens.get).

Show solution
import fleetlab

def startup_report(parts, calls):
    tokens = {name: fleetlab.estimate_tokens(text) for name, text in parts.items()}
    total = sum(tokens.values())
    return {"tokens": total, "per_run": total * calls, "largest": max(tokens, key=tokens.get)}

Write commands(md) that returns every command in backticks on a bullet line inside the ## Commands section of an AGENTS.md, in order. The section ends at the next line starting with ## . Only text in single backticks counts.

Hint

Walk the lines with an inside flag. Turn it on at ## Commands and off at any other line starting with ## . On bullet lines (starting with - ) collect re.findall(r"`([^`]+)`", line).

Show solution
import re

def commands(md):
    found, inside = [], False
    for line in md.splitlines():
        if line.startswith("## "):
            inside = line.strip() == "## Commands"
            continue
        if inside and line.lstrip().startswith("- "):
            found.extend(re.findall(r"`([^`]+)`", line))
    return found

Some tools only read the first limit bytes of AGENTS.md. Write hidden_headings(md, limit=16384) that returns the headings (lines starting with #) that start at or beyond byte limit of the UTF-8 encoded text, in order.

Hint

Keep a running byte offset: for each line (from splitlines(keepends=True)), check the offset before adding len(line.encode("utf-8")).

Show solution
def hidden_headings(md, limit=16384):
    hidden, offset = [], 0
    for line in md.splitlines(keepends=True):
        if offset >= limit and line.startswith("#"):
            hidden.append(line.rstrip("\n"))
        offset += len(line.encode("utf-8"))
    return hidden

Quiz

Recap

  • Startup context (CLAUDE.md, skill and agent descriptions, MCP tool definitions) is paid for on every request and competes for attention.
  • CLAUDE.md loads from your home, the project root, and subdirectories; @file imports. Keep shared instructions in AGENTS.md and import it.
  • AGENTS.md: commands that run, a map, a few rules. Delete lines that don't change behaviour.
  • Skills: .claude/skills/<name>/SKILL.md; metadata always, body when used, linked files when read.
  • Facts in AGENTS.md, procedures in skills, guarantees in hooks.
  • Delegate exploration, hand off files, size tasks to the window, and put lasting constraints in files.
