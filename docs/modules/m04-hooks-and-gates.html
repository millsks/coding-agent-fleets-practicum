Hooks and Gates

Instructions are requests. A hook is code that Claude Code runs at a fixed point in the loop, and it can stop the agent. That makes hooks the place where "never push to main" and "don't finish while the tests are red" become guarantees instead of hopes. This module covers how hooks are configured, what they receive, how they answer, and how to write and test the two gates every fleet needs: a guard on risky commands and a gate on finishing.

⏱ ~2.5 hoursPrerequisites: M03 Context Engineering

  • Configure hooks in settings with matchers, and predict which hooks run for a tool call
  • Read a hook's JSON payload and answer with the right exit code or JSON decision
  • Explain why exit 1 does not block, and what stop_hook_active prevents
  • Write and test a PreToolUse guard that blocks risky commands without blocking normal work
  • Write and test a Stop gate that keeps an agent working until checks pass

From requests to guarantees

Everything you've written so far is a guide: it steers the model, and the model usually follows. Usually isn't good enough for some rules. An agent working through a long task, reading an issue that contains instructions (shelf issue #5), or simply confused, will eventually do the thing you told it not to.

A hook is a command Claude Code runs at a specific point in the agent loop: before a tool runs, after it runs, when the agent tries to stop, and more. Hooks are deterministic code, they run every time their event fires, and some of them can block. That makes them the sensors of your harness, and the strongest one you have short of CI.

In AGENTS.md (a request)

- Never push to main.
- Run the tests before finishing.

As hooks (a guarantee)

  • A PreToolUse hook on Bash that blocks git push … main
  • A Stop hook that runs the tests and refuses to let the agent finish while they fail

Remember: keep the prose (it helps the agent plan), but enforce anything that matters with a hook, and back the most important rules with CI and branch protection too.

Hook events

Claude Code has many hook events. These are the ones a fleet relies on:

EventFiresCan block?Fleet use
PreToolUseBefore a tool runsYes: stops the callGuard risky commands, protect paths
PostToolUseAfter a tool succeedsNo (it already ran), but can feed backRun a formatter, report lint errors to the agent
PostToolUseFailureAfter a tool failsNoLog failures, add recovery hints
UserPromptSubmitWhen a prompt is submittedYesAdd context, refuse unsafe prompts
StopWhen the main agent tries to finishYes: keeps it workingThe "checks must pass" gate
SubagentStopWhen a subagent tries to finishYesPer-role gates
SessionStart, SessionEndSession begins or endsNoLoad context, write logs
PreCompactBefore compactionYesSave state before detail is summarised
TaskCompleted, TeammateIdleAgent teams: a task is marked done, a teammate goes idleYesQuality gates for teams (Stage 2)

This module builds one PreToolUse gate and one Stop gate. The same skills carry over to every other event.

Configuring hooks

Hooks live in settings files under "hooks", in three levels: the event, a matcher group that filters when it fires, and the hook handlers to run.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/guard_bash.py\"", "timeout": 30 }
        ]
      },
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/protect_paths.py\"" }
        ]
      }
    ],
    "Stop": [
      { "hooks": [ { "type": "command", "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/require_green.py\"" } ] }
    ]
  }
}

Matchers

  • Empty, *, or missing: every tool.
  • Only letters, digits, _, -, spaces, commas and |: exact tool names, or a list such as Edit|Write.
  • Anything else: an unanchored regular expression, such as ^Notebook or mcp__github__.*. A bare mcp__github matches nothing.

Commands and where hooks live

$CLAUDE_PROJECT_DIR is the project root where the session started, so hook paths work whatever directory the agent is in. The default timeout for a command hook is 600 seconds. Hooks can be configured in user, project, local, and managed settings, in plugins, in a skill's frontmatter, and in a subagent's frontmatter (where Stop becomes SubagentStop, so a gate applies only to that role). Hooks from every level are combined. Run /hooks in a session to see what's active.

What a hook receives

Claude Code starts your command and writes one JSON object to its standard input. Every event includes session_id, transcript_path, cwd, permission_mode, and hook_event_name. Then each event adds its own fields:

  • PreToolUse adds tool_name, tool_input (the tool's arguments: a command for Bash, a file_path for Edit and Write), and tool_use_id.
  • Stop adds stop_hook_active (true when the agent is already continuing because a Stop hook blocked it) and the agent's last_assistant_message.

Subagent hooks also receive agent_id and agent_type, so one hook can treat roles differently.

Answering: exit codes

The simplest way for a hook to answer is its exit code:

Exit codeMeaningWhat Claude sees
0Success; the action goes aheadNothing, unless stdout is one JSON object with a decision
2Blocking error: on events that can block, the action is stoppedYour stderr, as the reason
anything elseNon-blocking error: the action goes aheadA note that the hook failed

This is the most common hook bug. Python's sys.exit(1), an uncaught exception, or a shell script that fails all exit with codes other than 2, and Claude Code treats those as "the hook broke, carry on". A guard that crashes lets the dangerous command through. Use sys.exit(2) to block, and test the block path.

On exit 2, stderr is the message the agent reads, so write it for the agent: say what was blocked, why, and what to do instead. "Blocked: force pushes are not allowed. Push to a new branch and open a pull request." gives the agent a way forward. "Error" gives it nothing.

Answering: JSON decisions

For more control, exit 0 and print exactly one JSON object to stdout (nothing else around it). For PreToolUse, the decision goes under hookSpecificOutput:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Pushing to main is not allowed. Open a pull request."
  }
}

permissionDecision can be allow (skip the permission prompt), deny, ask (show the user a prompt), or defer. A PreToolUse hook can also return updatedInput to change the tool's arguments before it runs, and additionalContext to tell Claude something.

For Stop, the shape is simpler:

{ "decision": "block", "reason": "3 tests are failing: fix them before finishing." }

Which to use? Exit 2 with a stderr message is the simplest and works on every blocking event. Use JSON when you need ask, allow, or updatedInput. Remember that exit 2 blocks even if your JSON said allow, and that stdout is only read as a decision when it's a single JSON object.

Other tools speak different hook dialects. GitHub Copilot's hooks, for example, receive toolName and toolArgs and answer with permissionDecision JSON. If your fleet must run under several tools, keep the decision logic in one function and add a thin adapter per tool's format.

Gate 1: a guard on risky commands

A PreToolUse guard on Bash blocks commands that should never run without a human: rewriting shared history, pushing to the default branch, skipping git hooks, deleting outside the workspace, running scripts straight from the internet. Writing a good one is about balancing two kinds of error:

  • False negatives (a dangerous command gets through) are what you're preventing. Check the whole command string, not just its start: cd repo && git push --force must be caught.
  • False positives (normal work is blocked) are what makes people turn guards off. Pushing a feature branch, --force-with-lease on your own branch, and rm -rf build/ must pass.

Keep the rules as a list of (pattern, explanation) pairs, so the message for each block says exactly why. And test the guard like any other code, with a table of commands that must be blocked and commands that must be allowed. That table is the guard's specification.

A text-matching guard is a strong safety net, not a sandbox: an agent determined to work around it can write a Python script that does the same thing. Back the most important rules with something outside the agent's reach: branch protection on the server, credentials that can't push to main, a container without production access.

Gate 2: don't finish while checks fail

The Stop gate fixes the "premature done" failure from M01. When the agent tries to finish, the hook runs the project's fast checks. If they pass, it exits 0 and the agent stops. If they fail, it exits 2 with the end of the failure output on stderr, and Claude reads that as its next piece of work.

flowchart TD
  S[Agent tries to stop] --> A{stop_hook_active?}
  A -->|yes| OK[exit 0: let it stop]
  A -->|no| R[Run fast checks]
  R -->|pass| OK
  R -->|fail| B[exit 2 + tail of output on stderr]
  B --> W[Agent keeps working]
  W --> S

Three details make the difference between a gate and a trap:

  • stop_hook_active. When it's true, the agent is already continuing because of a Stop hook. If you block again, and the checks can't be fixed, the agent never stops. Let it go on the second attempt and let the orchestrator (Stage 2) treat the run as failed. That's the loop's exit.
  • The tail, not the whole log. Send the last 40 lines or so: that's where the failure summary is. A 2,000-line log fills the agent's context with noise.
  • A timeout. A hanging test suite would hang the agent. Run the checks with a timeout and block with a clear message if it's exceeded.

The checks themselves should be fast: this hook runs every time the agent tries to finish. A two-minute suite of unit tests is ideal; the full suite belongs in CI.

Testing hooks, and keeping them safe

Hooks are code that runs with your permissions on every matching event, so treat them like production code:

  • Test with recorded payloads. Build payloads with fleetlab.pre_tool_use and fleetlab.stop, or save real ones from a session, and assert on exit codes and messages. Test the allow path as well as the block path.
  • Keep them fast. A PreToolUse hook runs before every matching tool call.
  • Protect the hooks themselves. An agent that can edit .claude/settings.json or your hook scripts can switch its own gates off. Add them to your protected paths.
  • Know when repository hooks run. A headless claude -p run executes the hooks in a repository's .claude/settings.json without a trust prompt. In CI on untrusted pull requests, use --bare and pass the settings you trust with --settings.

Practice

Five exercises, each run with fleetlab.run_hook: your main() reads sys.stdin and calls sys.exit exactly as a real hook script does.

Write main() for a PreToolUse hook that exits 2 with a message on stderr when a Bash command contains rm -rf / or rm -rf ~ (followed by a space or the end of the command), and exits 0 otherwise, including for non-Bash tools.

Hint

re.search(r"rm\s+-rf\s+(/|~)(\s|$)", command) matches the dangerous forms but not /tmp/scratch, because / must be followed by a space or the end.

Show solution
import json, re, sys

def main():
    payload = json.load(sys.stdin)
    if payload.get("tool_name") != "Bash":
        sys.exit(0)
    command = payload.get("tool_input", {}).get("command", "")
    if re.search(r"rm\s+-rf\s+(/|~)(\s|$)", command):
        print("Blocked: recursive delete of / or your home directory.", file=sys.stderr)
        sys.exit(2)
    sys.exit(0)

Write main() for a hook matched to Edit|Write. Block (exit 2, message on stderr) when tool_input["file_path"], made relative to the payload's cwd if it's inside it, matches any glob in PROTECTED using fnmatch. Allow everything else.

Hint

If path.startswith(cwd + "/"), slice it off. Then any(fnmatch.fnmatch(rel, p) for p in PROTECTED).

Show solution
import fnmatch, json, sys

PROTECTED = [".github/workflows/*", ".claude/*", ".env", "tests/*"]

def main():
    payload = json.load(sys.stdin)
    path = payload.get("tool_input", {}).get("file_path", "")
    cwd = payload.get("cwd", "")
    rel = path[len(cwd) + 1:] if cwd and path.startswith(cwd + "/") else path
    for pattern in PROTECTED:
        if fnmatch.fnmatch(rel, pattern):
            print(f"Blocked: {rel} is protected ({pattern}). Explain the needed change in your summary instead.", file=sys.stderr)
            sys.exit(2)
    sys.exit(0)

Write main() that denies git push commands targeting main or master by exiting 0 and printing a single JSON object with hookSpecificOutput.permissionDecision = "deny" and a reason. For every other command print nothing and exit 0.

Hint

Match main or master as a whole word not followed by -: re.search(r"\bgit\s+push\b.*\s(HEAD:)?(main|master)\b(?!-)", cmd). Print with print(json.dumps(...)).

def main():

    cmd = payload.get("tool_input", {}).get("command", "")

Write make_stop_hook(run_checks). run_checks() returns (exit_code, output) from the project's fast checks. Return a main() that:

  • exits 0 immediately if the payload's stop_hook_active is true (without running checks);
  • exits 0 if the checks pass;
  • otherwise prints Checks failed and the last 5 lines of the output to stderr, and exits 2.
Hint

Read the payload first and check payload.get("stop_hook_active"). Use output.splitlines()[-5:].

Show solution
import json, sys

def make_stop_hook(run_checks):
    def main():
        payload = json.load(sys.stdin)
        if payload.get("stop_hook_active"):
            sys.exit(0)
        code, output = run_checks()
        if code == 0:
            sys.exit(0)
        print("Checks failed. Fix them before finishing:", file=sys.stderr)
        print("\n".join(output.splitlines()[-5:]), file=sys.stderr)
        sys.exit(2)
    return main

Quiz

Recap

  • Hooks turn rules into guarantees. Guides steer; hooks (and CI) enforce.
  • Configure under "hooks": event, matcher group, handlers. Matchers are exact names, |-lists, or regular expressions. Use $CLAUDE_PROJECT_DIR.
  • Payload on stdin: common fields plus tool_name/tool_input for PreToolUse and stop_hook_active for Stop.
  • Exit 0 continues, exit 2 blocks with stderr as the reason, anything else is a non-blocking error. exit 1 does not block.
  • JSON: hookSpecificOutput.permissionDecision for PreToolUse; {"decision": "block"} for Stop.
  • Guards balance false negatives and false positives; test both from a table. Stop gates honour stop_hook_active, send the tail, and use a timeout.
  • Test hooks with recorded payloads, keep them fast, protect them, and use --bare on untrusted input.
